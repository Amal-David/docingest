# Integration checklist | Coda Distribution Platform Technical Documentation

For the complete documentation index, see [llms.txt](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/llms.txt)
. This page is also available as [Markdown](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/integration-checklist.md)
.

Follow this checklist to prepare your distribution account for launch. We suggest to read through all the documentation before coming back here again.

*   Review the API documentation and plan your integration
    
*   (If you are buying direct-topup product) - Read [Direct topup purchase flow](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/direct-topup-purchase-flow)
     guide
    
*   Access your account in the distribution portal (request access from your account manager if you don't have access)
    
*   [Get API Credentials](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/getting-api-credentials-ip-whitelisting-and-postman-collection)
     and whitelist your IP in sandbox & production in distributor portal
    
*   Download postman collection from distributor portal and test it locally
    
*   [Start API integration](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/api-references)
    
    *   [Handle timeout and retry mechanism](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/timeout-and-handling-retries)
        
    
*   Test the various purchase flow for following products in a [sandbox environment](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/sandbox-environment):
    
    *   Voucher
        
    *   Direct-topup with subtype = 1 (userid)
        
    *   Direct-topup with subtype = 2 (userid, serverlist)
        
    *   Direct-topup with subtype = 3 (userid, zoneid)
        
    *   Direct-topup with haveRole = True
        
    
*   (If under prepayment model) [Make a prepayment submission](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/distributor-portal/managing-prepaid-balance/topping-up-prepaid-balance)
    
*   Ensure production credentials are correct
    
*   Request for assets (product images, description) from your account manager or Coda support team or download it directly from codashop.com
    
*   Launch

# Getting API credentials, IP Whitelisting, and Postman Collection | Coda Distribution Platform Technical Documentation

For the complete documentation index, see [llms.txt](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/llms.txt)
. This page is also available as [Markdown](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/getting-api-credentials-ip-whitelisting-and-postman-collection.md)
.

To obtain your API key, download our Postman API collection, and whitelist your IP addresses, navigate to Settings -> Integration tab. You would require to setup MFA authenticator before accessing this page

*   **API Key and Postman Collection:** Access the page to obtain your API key and download our Postman API collection.
    
*   **Key Expiry:** Note that the API secret key expires after 365 days. You will need to refresh it before it expires. You can have two secret keys at the same time for renewal purposes.
    
*   **IP Whitelisting:** Ensure all your IP addresses are added to the IP whitelist. Failure to whitelist IPs may result in rejection of your API requests.
    

Note that the IP whitelist and credentials are different between production and sandbox environment. You need to whitelist the IP in both environment and also use the respective API credentials when doing sandbox or production testing.

# Direct topup purchase flow | Coda Distribution Platform Technical Documentation

For the complete documentation index, see [llms.txt](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/llms.txt)
. This page is also available as [Markdown](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/direct-topup-purchase-flow.md)
.

Transaction processing flow[](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/direct-topup-purchase-flow#transaction-processing-flow)

------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

_API References:_ [Direct-topup purchase](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/api-references/direct-topup-purchase)

Direct topup products will require two steps to place an order

*   **Validate API**: to validate whether the request sent from the partner system is correct by checking the following information:
    
    1.  Whether user account information entered is correct or not.
        
    2.  Whether the SKU is valid, and if the user is eligible to buy the SKU.
        
    3.  Whether the price entered is valid or not. We do price validation based on the listSKU response and validate requests to make sure you send the right price to us
        
    
*   **Topup API**: to top-up in-game products to the user account:
    
    *   Response of validate will contain orderId which must be passed as part of topup.
        
    *   Top-up must occur within 7 days of the validation call. Failure to do so will result in an order expiry error, as all initiated orders (those successfully validated) expire after 7 days if not topped up within that timeframe.
        
    

We will only charge you for successful top-up requests. Orders that are validated but do not result in any successful top-ups will not incur any charges.

![](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/~gitbook/image?url=https%3A%2F%2F532338858-files.gitbook.io%2F%7E%2Ffiles%2Fv0%2Fb%2Fgitbook-x-prod.appspot.com%2Fo%2Fspaces%252FeJPadAPb8Few47C1v6hy%252Fuploads%252FLfn24zifCduzWDaR19xl%252Fimage.png%3Falt%3Dmedia%26token%3Dc985c6db-9323-482c-90e1-e922a7e181e3&width=768&dpr=3&quality=100&sign=abbc8b75&sv=2)

* * *

Type of game account to collect from end-user[](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/direct-topup-purchase-flow#type-of-game-account-to-collect-from-end-user)

------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

Various games have different types of game account information required. There are two pieces of information that you need to consider:

*   Game account info type (`subtype`)
    
    *   Userid only (`subtype=1`)
        
    *   Userid and server list selection (`subtype=2`)
        
        *   Require partner to ask user to select server from a predefined server list, which is supported in our [listServer API](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/api-references/direct-topup-purchase)
            )
            
        
    *   Userid and zoneid (`subtype=3`)
        
        *   zoneid is the region information from the game
            
        
    
*   If role selection is required (`haveRole=True`)
    
    *   Some games have multiple accounts / roles from a userid, this is called "role" in Coda context. After validating the userid, the user will need to select which role the topup is meant for.
        
    *   If True, you will need to ask user for their role upon successful **validate** request. **Validate** will return a role list and partner need to display the role selection UI to select the role. The the roleId will need to be passed to the **topup** request.

For the complete documentation index, see [llms.txt](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/llms.txt)
. This page is also available as [Markdown](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/timeout-and-handling-retries.md)
.

Our API is semi-idempotent. You can retry any method using the same `requestId` to check the status of the original request. However, each new request requires an updated `iat` (issued at) timestamp. Reusing the same `requestId` will not create a new record; it will return the same result as the previous request.

We recommend to set a timeout of 12 seconds for all API methods.

Make sure the iat (issued at) is within 5 minutes from when the request is made, anything more than that will result in an error.

**Voucher Products:**

*   **placeOrder**: We set a timeout of 10 seconds for responses from our merchant partners. If we do not receive a response within this time, we will return a Failure. You can retry with the same `requestId` and a new `iat`.
    
*   **getOrder**: Only use `getOrder` if you have already received a response from `placeOrder`. If you haven’t received a response from `placeOrder`, retry `placeOrder` with a new `iat`.
    

**Topup Products:**

*   **validate**: We set a timeout of 10 seconds for responses from our merchant partners, and 5 seconds for Mobile Legends. If there is no response within this timeframe, we will return a Failure. You can retry the `validate`request with a new `iat`.
    
    *   Note: For `validate` the same request may not always return the same response. For instance, a `userId`might be eligible for a specific SKU on one day but not on another.
        
    
*   **topup**: We always reply instantly with `FULFILLED`. If a timeout occurs on the merchant side, we handle retries internally. If you receive no reply, simply retry the `topup` request with the same payload and a new `iat`.

# Secret key rotation | Coda Distribution Platform Technical Documentation

For the complete documentation index, see [llms.txt](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/llms.txt)
. This page is also available as [Markdown](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/integration-guides/secret-key-rotation.md)
.

Your secret key is valid for 365 days. To maintain security and compliance with standards, partners must update their secret key before it expires.

There are two methods for secret key rotation:

1.  **On-Demand Rotation**: The key will expire one year after it is rotated.
    
2.  **Annual Auto-Rotation**: The key is automatically rotated once a year.
    

To check the expiration date of your current key and obtain a new one, follow these steps in the distributor portal:

1.  Navigate to the **Settings** section.
    
2.  Go to **Integration** (enable MFA if it is not already enabled).
    
3.  Review the expiration date of your current key and retrieve the new secret key.
    

Ensure you update your key before the expiration date to avoid transaction issues.

# Transaction reports | Coda Distribution Platform Technical Documentation

. This page is also available as [Markdown](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/distributor-portal/transaction-reports.md)

You can access and download your historical transactions from the distributor portal under the Transactions tab.

For direct-topup orders initiated after a 'validate' request, they remain valid for 7 days. During this period, partners can continue to make top-up requests. After 7 days, any orders without a top-up request will be automatically cancelled and marked as Failed. Orders that have failed the 'validate' request will not appear in the transaction history.

We offer several filters to enhance your search:

*   **Country**: Source country of the SKU for the order.
    
*   **Product**: Name of the game or product.
    
*   **Timezone**: Display configuration of dates in the order table.
    
*   **OrderID**: Unique identifier for the order.
    
*   **Bulk Txn ID**: Transaction ID from bulk purchases made via the distributor portal.
    
*   **Request ID**: Partner ID sent from the API request.
    
*   **Status**:
    
    *   **New**: Direct top-up order validated but not yet top-up requested.
        
    *   **Fulfilled**: Direct top-up order with a top-up request. All voucher orders are marked with this status.
        
    *   **Failed**: Direct top-up order that has failed after 7 days without a top-up request.

# Request header & Authentication | Coda Distribution Platform Technical Documentation

Coda xShop API is using `x-api-key` and auth token to authenticate your requests in the header. The authentication data ( `x-api-key`, `x-client-id` , `secret`) that is used to generate the authentication token can be fetched from [Integration Settings](https://distributor-portal.codapayments.com/settings)
 of your distributor portal

### `Bearer <token>` generation method[](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/api-references/request-header-and-authentication#bearer-less-than-token-greater-than-generation-method)

*   We use JSON Web Token generated based on header, payload, and signature. => [https://jwt.io/](https://jwt.io/introduction)
    
*   JSON Web Token consist of three parts separated by dots(.) which are: header.payload.signature
    
    *   Header: `alg`, `typ`, `x-api-key`, `x-api-version`, `x-client-id`
        
        *   `alg` must be "HS256", `typ` must be "JWT", and `x-api-version` must be "2.0"
            
        *   `x-api-key` and `x-client-id` can be fetched from the distributor portal
            
        
    *   Payload: payload used for the API call. Will be different for all API calls. **This needs to be stringified** when generating JWT token
        
    *   Signature: encoded key based on `header`, `payload`, and `secret`
        
        *   `secret` can be fetched from distributor portal
            
        
    
*   The easiest way to generate a JWT token is by using a jwt library, and can be found in [https://jwt.io/#libraries-io](https://jwt.io/#libraries-io)
    
*   Below is the sample of header, payload, and signature to generate the authorization token

    function base64url(source) {
      // Encode in classical base64
      encodedSource = CryptoJS.enc.Base64.stringify(source);
    
      // Remove padding equal characters
      encodedSource = encodedSource.replace(/=+$/, '');
    
      // Replace characters according to base64url specifications
      encodedSource = encodedSource.replace(/\+/g, '-');
      encodedSource = encodedSource.replace(/\//g, '_');
    
      return encodedSource;
    }

      public static String generate(final String data, final String key) throws NoSuchAlgorithmException, InvalidKeyException {
        if (key == null || data == null) throw new NullPointerException();
        final Mac hMacSHA256 = Mac.getInstance(HMAC_SHA256);
        byte[] hmacKeyBytes = key.getBytes(StandardCharsets.UTF_8);
        final SecretKeySpec secretKey = new SecretKeySpec(hmacKeyBytes, HMAC_SHA256);
        hMacSHA256.init(secretKey);
        byte[] dataBytes = data.getBytes(StandardCharsets.UTF_8);
        byte[] res = hMacSHA256.doFinal(dataBytes);
        return Base64.getUrlEncoder().withoutPadding().encodeToString(res);
      }

The Top-up Interface is for placing orders to directly top-up a user account for product with type = `topup`

As we are using JSON-RPC 2.0, The `/{product-name}` endpoint supports different kind of operations and differentiated through the `method` payload:

1.  [Direct-topup purchase](https://coda-payments.gitbook.io/coda-distribution-technical-documentation/api-references/direct-topup-purchase#product-name)

# Direct topup purchase flow

## Transaction processing flow

\*API References:\* \[Direct-topup purchase\](/coda-distribution-technical-documentation/api-references/direct-topup-purchase.md)

Direct topup products will require two steps to place an order

\* \*\*Validate API\*\*: to validate whether the request sent from the partner system is correct by checking the following information:
  1. Whether user account information entered is correct or not.&#x20;
  2. Whether the SKU is valid, and if the user is eligible to buy the SKU.&#x20;
  3. Whether the price entered is valid or not. We do price validation based on the listSKU response and validate requests to make sure you send the right price to us
\* \*\*Topup API\*\*: to top-up in-game products to the user account:
  \* Response of validate will contain orderId which must be passed as part of topup.&#x20;
  \* Top-up must occur within 7 days of the validation call. Failure to do so will result in an order expiry error, as all initiated orders (those successfully validated) expire after 7 days if not topped up within that timeframe.

{% hint style="info" %}
We will only charge you for successful top-up requests. Orders that are validated but do not result in any successful top-ups will not incur any charges.
{% endhint %}

## Type of game account to collect from end-user

Various games have different types of game account information required. There are two pieces of information that you need to consider:

\* Game account info type (\`subtype\`)
  \* Userid only (\`subtype=1\`)
  \* Userid and server list selection (\`subtype=2\`)&#x20;
    \* Require partner to ask user to select server from a predefined server list, which is supported in our \[listServer API\](/coda-distribution-technical-documentation/api-references/direct-topup-purchase.md))
  \* Userid and zoneid  (\`subtype=3\`)&#x20;
    \* zoneid is the region information from the game
\* If role selection is required (\`haveRole=True\`)
  \* Some games have multiple accounts / roles from a userid, this is called "role" in Coda context. After validating the userid, the user will need to select which role the topup is meant for.
  \* If True, you will need to ask user for their role upon successful \*\*validate\*\* request. \*\*Validate\*\* will return a role list and partner need to display the role selection UI to select the role. The the roleId will need to be passed to the \*\*topup\*\* request.

# Timeout and handling retries

Our API is semi-idempotent. You can retry any method using the same \`requestId\` to check the status of the original request. However, each new request requires an updated \`iat\` (issued at) timestamp. Reusing the same \`requestId\` will not create a new record; it will return the same result as the previous request.

We recommend to set a timeout of 12 seconds for all API methods.

{% hint style="info" %}
Make sure the iat (issued at) is within 5 minutes from when the request is made, anything more than that will result in an error.
{% endhint %}

\*\*Voucher Products:\*\*

\* \*\*placeOrder\*\*: We set a timeout of 10 seconds for responses from our merchant partners. If we do not receive a response within this time, we will return a Failure. You can retry with the same \`requestId\` and a new \`iat\`.
\* \*\*getOrder\*\*: Only use \`getOrder\` if you have already received a response from \`placeOrder\`. If you haven’t received a response from \`placeOrder\`, retry \`placeOrder\` with a new \`iat\`.

\*\*Topup Products:\*\*

\* \*\*validate\*\*: We set a timeout of 10 seconds for responses from our merchant partners, and 5 seconds for Mobile Legends. If there is no response within this timeframe, we will return a Failure. You can retry the \`validate\`request with a new \`iat\`.
  \* Note: For \`validate\` the same request may not always return the same response. For instance, a \`userId\`might be eligible for a specific SKU on one day but not on another.
\* \*\*topup\*\*: We always reply instantly with \`FULFILLED\`. If a timeout occurs on the merchant side, we handle retries internally. If you receive no reply, simply retry the \`topup\` request with the same payload and a new \`iat\`.

# Secret key rotation

Your secret key is valid for 365 days. To maintain security and compliance with standards, partners must update their secret key before it expires.

There are two methods for secret key rotation:

1. \*\*On-Demand Rotation\*\*: The key will expire one year after it is rotated.
2. \*\*Annual Auto-Rotation\*\*: The key is automatically rotated once a year.

To check the expiration date of your current key and obtain a new one, follow these steps in the distributor portal:

1. Navigate to the \*\*Settings\*\* section.
2. Go to \*\*Integration\*\* (enable MFA if it is not already enabled).
3. Review the expiration date of your current key and retrieve the new secret key.

{% hint style="info" %}
Ensure you update your key before the expiration date to avoid transaction issues.
{% endhint %}

# Request header & Authentication

Coda xShop API is using \`x-api-key\` and auth token to authenticate your requests in the header. The authentication data ( \`x-api-key\`, \`x-client-id\` , \`secret\`) that is used to generate the authentication token can be fetched from \[Integration Settings\](https://distributor-portal.codapayments.com/settings) of your distributor portal

### Request Headers

<table><thead><tr><th width="262">Name</th><th>Value</th></tr></thead><tbody><tr><td>Content-Type</td><td><code>application/json</code></td></tr><tr><td>x-api-key</td><td><code>&#x3C;x-api-key></code></td></tr><tr><td>x-api-version</td><td><code>2.0</code></td></tr><tr><td>Authorization</td><td><code>Bearer &#x3C;token></code></td></tr></tbody></table>

### \`Bearer <token>\`  generation method

\* We use JSON Web Token generated based on header, payload, and signature. => \[https://jwt.io/\](https://jwt.io/introduction)
\* JSON Web Token consist of three parts separated by dots(.) which are: header.payload.signature
  \* Header: \`alg\`, \`typ\`, \`x-api-key\`, \`x-api-version\`, \`x-client-id\`
    \* \`alg\` must be "HS256", \`typ\` must be "JWT", and \`x-api-version\` must be "2.0"
    \* \`x-api-key\` and \`x-client-id\` can be fetched from the distributor portal
  \* Payload: payload used for the API call. Will be different for all API calls. \*\*This needs to be stringified\*\* when generating JWT token
  \* Signature: encoded key based on \`header\`, \`payload\`, and \`secret\`
    \* \`secret\` can be fetched from distributor portal
\* The easiest way to generate a JWT token is by using a jwt library, and can be found in <https://jwt.io/#libraries-io>
\* Below is the sample of header, payload, and signature to generate the authorization token

function base64url(source) {
  // Encode in classical base64
  encodedSource = CryptoJS.enc.Base64.stringify(source);

  // Remove padding equal characters
  encodedSource = encodedSource.replace(/=+$/, '');

  // Replace characters according to base64url specifications
  encodedSource = encodedSource.replace(/\\+/g, '-');
  encodedSource = encodedSource.replace(/\\//g, '\_');

  return encodedSource;
}

function getIAT() {
    return Math.floor(Date.now() / 1000) + 257;
}

# Direct-topup purchase

The Top-up Interface is for placing orders to directly top-up a user account for product with type = \`topup\`

As we are using JSON-RPC 2.0,  The \`/{product-name}\` endpoint supports different kind of operations and differentiated through the \`method\` payload:

1. \[#product-name\](#product-name "mention") with \`"method" = "listServer"\`- Get server list selection (only for product with subtype = 2)
2. \[#product-name-1\](#product-name-1 "mention") with \`"method"="validate"\` - Validate userid and eligibility to buy skuid (step 1 of order flow). This will generate a new order with status = NEW and need to continue with topup to complete the order.
3. \[#product-name-2\](#product-name-2 "mention") with \`"method" = "topup"\` - Topup the userid after successful validate (step 2 of order flow). Your account will only be charged after topup is successful

# Transaction reports

You can access and download your historical transactions from the distributor portal under the Transactions tab.

For direct-topup orders initiated after a 'validate' request, they remain valid for 7 days. During this period, partners can continue to make top-up requests. After 7 days, any orders without a top-up request will be automatically cancelled and marked as Failed. Orders that have failed the 'validate' request will not appear in the transaction history.&#x20;

We offer several filters to enhance your search:

\* \*\*Country\*\*: Source country of the SKU for the order.
\* \*\*Product\*\*: Name of the game or product.
\* \*\*Timezone\*\*: Display configuration of dates in the order table.
\* \*\*OrderID\*\*: Unique identifier for the order.
\* \*\*Bulk Txn ID\*\*: Transaction ID from bulk purchases made via the distributor portal.
\* \*\*Request ID\*\*: Partner ID sent from the API request.
\* \*\*Status\*\*:
  \* \*\*New\*\*: Direct top-up order validated but not yet top-up requested.
  \* \*\*Fulfilled\*\*: Direct top-up order with a top-up request. All voucher orders are marked with this status.
  \* \*\*Failed\*\*: Direct top-up order that has failed after 7 days without a top-up request.

{% hint style="info" %}
Our reports default to displaying timezone in UTC. You can adjust the timezone display in the expanded filter options within the order history.
{% endhint %}

# Deciding which balance to use

We support two options for you to manage your balance in buying product from us

1. \*\*USD Pricing and deduct USD wallet:\*\*
   \* We convert local currency SKU pricing to USD daily, and we will deduct your USD balance to process your order
   \* Our FX rates are refreshed at 12:30AM UTC. Ensure you fetch the updated prices post-refresh to avoid transaction failures due to price validation checks.
     \* We source our FX rates from \[xignite\](https://www.xignite.com/faqs/cryptocurrency-and-fx-rates/where-does-the-xignite-fx-rates-data-come-from/) and add a spread to manage the day-to-day fluctuation (spread may be different from country-to-country).&#x20;
2. \*\*Local Currency (LCY) Pricing and deduct LCY credit balance:\*\*
   \* You can send payment directly according to the LCY and we will topup your LCY wallet
   \* We also support \[wallet conversion feature\](/coda-distribution-technical-documentation/distributor-portal/managing-prepaid-balance/transferring-balance-across-wallet-currency.md) if you can't send payment in local currency to help you manage your balance and funds with us

# Purchasing direct top-up and voucher codes

In addition to using the API, you can purchase vouchers or top-ups directly from the distributor portal under the Top-Up menu

When making transactions, if you are on a prepayment, we will deduct the balance according to the transaction amount and currency.

For purchasing voucher codes, you can bulk purchase up to 20,000 codes per transaction. The codes will be delivered to the requester via email. Note some codes may not support bulk purchase as it's dependent on the supplier of the codes
